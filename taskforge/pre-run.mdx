---
title: "Pre-run checks"
description: "Test the grader before any agent runs: the reference must earn the reward, the untouched code must not, and the reward must not be reachable without solving the task."
---

A benchmark's pass rate means something only when its grader is right. Pre-run checks prove that before you pay for rollouts.

## Task CI: `run_task_ci_checks`

Run it on a complete draft (instruction, Dockerfile, code, `test.sh`, `solve.sh`), and again after each change to the instruction, the verifier or the environment.

```json
run_task_ci_checks {"repo": "acme/tasks", "ref": "main", "path": "tasks/fix-rounding"}
```

Stop when the report's `eval_ready` is true. The report lands at `<task>/ci/<run id>/report.json`. Several bundles at once: pass `paths`; each runs in a container of its own under one run id.

Three stages, cheapest first:

| Stage | Checks | Decides `eval_ready` |
| --- | --- | --- |
| Screen | `harbor_config`, `agent_network`, `solve_sh_runnable`, `test_setup_runnable`, `instruction_leakage`, `instruction_private_details` | No, but a failure holds every sandbox back |
| | `harbor_structure`, `dockerfile_sanity`, `solution_format`, `test_file_references` | Advisory |
| Audits | `task_reference`, `task_eval_signal`, `instruction_flags`, `test_not_fragile`, `test_data_driven`, `test_quality` | Never: recorded as advice in `gate.advisory_failed` |
| Arms | `bundle_shape`, `cross_case_distinct`, `bundle_private_details` (read off the files) | Yes |
| | The sandboxed arms below, run only where the screen passed, and `reward_readable`, read off the oracle's own trials | Yes |

| Arm | Proves |
| --- | --- |
| oracle | The reference solution scores 1.0. Run three times; the repeats must agree |
| null | The untouched codebase scores below 1.0. Run three times |
| baseline | Every case that fails on the untouched code fails on an observable it declared, never on an infrastructure reason, and at least one case discriminates |
| seeded fault | Every wrong solution is caught by a case, and every right solution scores 1.0. One sandbox per solution; the most expensive arm |
| pass-to-pass | The behaviour the change must keep held with the reference applied and on the untouched code |
| adversarial | Rewriting every file outside the declared deliverable cannot reach the reward |

What the newer checks ask:

| Check | Fails when |
| --- | --- |
| `agent_network` | The agent phase can reach a network. Harbor's `[environment] network_mode` defaults to `public`, so set `[agent] network_mode = "no-network"` (or `[environment] allow_internet = false`). A task that needs a network declares the mode and says why under `[metadata] network_reason` |
| `reward_readable` | A reward file the oracle published (`/logs/verifier/reward.txt` or `reward.json`) is not readable by a non-root reader, as with `tempfile.mkstemp` (mode 0600). Harbor's local Docker backend then cannot read the reward. Write it world-readable |
| `solve_sh_runnable` | `solve.sh` is missing, fails `bash -n`, or runs no command (only comments, `echo` or blank lines). Any command counts; whether it solves the task is the oracle arm's |
| `bundle_shape` | Besides an undeclared entry, any editor or patch leftover anywhere in the bundle: `*-E` (BSD `sed -i`), `*.orig`, `*.rej`, `*~`, `.*.swp`, `.DS_Store`. A bundle is held to a grading interface's shape only when it declares one: `recorded` is declared by a `case.json` in each case directory (`tests/cases/<case>/case.json`). A bundle that declares none, whatever directories it carries, gets the generic shape |
| `instruction_flags` (advisory) | Flag `hidden_interface`: the tests depend on a symbol, signature, CLI or path that `instruction.md` never states |

The oracle arm runs the bundle exactly as shipped, through Harbor's own oracle agent, so a reference that touches a path missing from `environment/` scores 0 there.

`eval_ready` is a claim about what ran: the screen passed, every arm ran and passed, and every soundness leg measured something. Nothing excuses a finding. Pass `arms: false` to screen and audit only; that run is never `eval_ready`. Anything short of `eval_ready` names what refused in `gate.blocking_checks`, `gate.unmeasured` and `gate.reason`.

## Soundness

A reward is sound when every right solution scores 1.0 and every wrong one scores below 1.0. Unknown is red: a soundness leg that measured nothing holds `eval_ready` back exactly as a failure does.

| Soundness leg | Measured when | `gate.reason` when not |
| --- | --- | --- |
| `oracle` | The reference solution was graded | `the reference solution was not graded` |
| `null_arm` | The untouched code was graded | `the untouched code was not graded` |
| `seeded_fault_arm` | The bundle offers at least one wrong solution, and each was graded | `no wrong solutions offered` |

`gate.soundness_legs` lists the three, `gate.unmeasured` the ones that measured nothing, and `gate.reason` says what is missing in one sentence, for example `no wrong solutions offered: see https://docs.metaphi.ai/taskforge/pre-run#soundness`.

### Wrong and right solutions

They live in the bundle, under `tests/`:

```
tests/
├── test.sh
├── wrong/<name>.patch     or  wrong/<name>/…    must score below 1.0
└── right/<name>.patch     or  right/<name>/…    must score 1.0
```

Harbor never shows `tests/` to the agent: it copies the directory to `/tests` for the verifier once the agent has stopped, or builds a separate verifier container from it. `solution/` reaches only the oracle agent.

Two formats, the same for both kinds:

| Format | What it is | How it is applied |
| --- | --- | --- |
| Patch | A `.patch` or `.diff` file | `git apply` in the image's working directory (the image needs `git`) |
| Overlay | A directory | Its files are copied over the working directory at their relative paths. A `solve.sh` at its top is ignored |

The working directory is the one Harbor runs the reference in: `[environment] workdir`, else the Dockerfile's `WORKDIR`. A task whose agent writes an answer rather than changing code uses an overlay holding that answer, for example `tests/wrong/sign-flipped/answer.json` where the working directory is `/workspace` and the verifier reads `/workspace/answer.json`.

Each solution replaces the reference in a copy of the bundle and runs through Harbor's oracle agent and the bundle's own verifier, in a sandbox of its own. A wrong solution passes when a case rejects it (with no per-case report, when the reward is below 1.0). A right solution passes at 1.0. A solution that does not apply (a patch that fails, a copy that errors) fails the arm; it is never counted as caught. Anything else under `tests/wrong` or `tests/right` (a loose file that is not a patch) fails the arm by name.

At least one wrong solution is required. Right solutions are optional (the reference is the one the oracle arm measures), but each one offered must score 1.0. A wrong solution that survives means a case is missing: add the case. A right solution that fails means a case grades the shape of the code.

Older bundles keep solutions beside the bundle, as `faults/<name>/` (wrong) and `variants/<name>/` (right) next to `<problem>/harbor/`, overlays only. They are still read. The report records each solution's `source` and `format`.

### Pass-to-pass

The verifier reports whether the behaviour the change must keep still holds. The arms read it, in this order:

1. The `pass_to_pass` key of `/logs/verifier/reward.json`: `1` (or any number at or above 1.0) when every pass-to-pass case held, less when one broke.
2. `/logs/verifier/p2p.txt`: `1` or `pass` when they held, `0` or `fail` when not.
3. Per-case rows of `grade.json` or `report.json` in `/logs/verifier/` whose `kind` is `pass_to_pass`.

`ctrf.json` alone reports no pass-to-pass outcome: its rows carry no kind. Write `p2p.txt` beside it.

It must hold with the reference applied and on the untouched code: a reported failure on either side blocks `eval_ready`. A verifier that reports none (the agent writes an answer from its inputs, so there is no prior behaviour) is recorded `skipped` and holds nothing back.

## Validate: `run_harbor_tasks` mode `validate`

The same questions through Harbor, one trial per leg, as a run will see the task.

```json
run_harbor_tasks {"repo": "acme/tasks", "ref": "main", "paths": ["tasks/fix-rounding"], "mode": "validate"}
```

| Leg | Passes when |
| --- | --- |
| `oracle` | `solve.sh` scores 1.0 |
| `null_arm` | No agent action scores below 1.0. A bundle graded under `gated-binary/1` must score exactly 0.0, with at least one fail-to-pass case, none of them passing, and every pass-to-pass case passing |
| `probe_cheat` | The oracle with a non-solving `solve.sh` scores below 1.0 |
| `probe_unsolved` | The bundle's first wrong solution (`tests/wrong/`) scores below 1.0. Skipped, by name, when the bundle offers none |

Mode `full` adds one `conduct` rollout with the first model. It lands at `<task>/validate/<run id>/`.

## Construction only: `prerun_validate`

Task CI's screen and audits on one bundle (structure, verifier setup, instruction and test quality), with no sandbox and no rollout. Returns passed, what is missing and what warns. A fast first look.
