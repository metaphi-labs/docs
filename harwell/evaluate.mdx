This topic shows how to run your own application on Harwell. You declare the codebase, compile it, and then run one batch job and one CICS transaction. You then compare the results with the output that the mainframe produces for the same input.

**Prerequisites**

- Your account has Harwell access. To request access, contact your Metaphi account team.
- [Hum](/overview) is installed. You run Harwell from Hum by describing the task, for example "submit the nightly settlement job" or "start transaction CUST and press Enter".
- For the batch job and the transaction that you choose, you have the mainframe's output for a known input.

## Step 1: Declare the codebase

Harwell runs your code in its existing directory layout. A `harwell.toml` file at the codebase root declares where Harwell finds each kind of member.

**To declare the codebase**

1. Create `harwell.toml` at the root of the codebase.
2. Declare the search orders, the Db2 catalog and the program control table. For example:

   ```toml
   [site]
   search_order = ["progs", "subprogs"]        # program libraries, searched in order
   procedure_order = ["procs"]                  # JCL and cataloged procedures
   db2_catalog = [                              # DDL and seed rows, applied before a run with no saved state
     "DB2/app_ddl.sql",
     "DB2/app_seed.sql",
   ]

   [site.region.transactions]                   # program control table
   CUST = "CUSTMNT"
   ```

All keys are optional. Harwell rejects an unknown key and names it. Instead of `[site.region]`, you can supply the CSD source of your region. For all keys, see [Batch jobs](/harwell/batch-runs#codebase) and [CICS transactions](/harwell/online-runs#region).

## Step 2: Compile the codebase

A compile run compiles program members and runs nothing. Use it to find what prevents your code from running before you run any job.

**To compile the codebase**

1. Request a compile of the program members, or of all members in the program libraries.
2. In the report, read one job for each program. A job with status `ok` compiled with return code 0 and no error-severity message. Warnings do not cause a failure.
3. For each job with status `failed`, read `stage` and `first_error`. `stage` identifies the tool that issued the first error: `dialect`, `adasql`, `cics`, `gixpp`, `cobc` or `link`.
4. Group the failures by first error. Typical causes are a missing copybook, a construct that the dialect does not support, and `EXEC DLI`, which has no IMS translator.
5. Check each failure against [Supported features](/harwell/what-runs).

Each compiled step carries a `compile_record`: the exact command line, the compiler version, the messages, the module with its SHA-256 digest, and a source listing.

## Step 3: Run a batch job

**To run a batch job**

1. Make sure that the codebase contains the JCL, the programs and copybooks that the job reaches, the input data sets, and the Db2 DDL and seed rows. Supply each data set as one file per data set name, with its LRECL and RECFM.
2. Submit the job by member name. To run several jobs as a stream, submit them together. Harwell runs each job after the jobs that it depends on, under one run clock.
3. In the report, check that `status` is `ok` and that each step's `rc` is the return code that the mainframe gives.
4. Compare the data sets and tables that the run left with the mainframe's output.

For a description of how Harwell runs a job, see [Batch jobs](/harwell/batch-runs).

## Step 4: Run a CICS transaction

**To run a CICS transaction**

1. Make sure that the codebase contains the transaction's programs and copybooks, its BMS source, and seed rows for the tables and files that it reads.
2. List every screen that a user sends, in order, starting with the transaction ID entry.
3. Start the transaction with those screens.
4. In the report, read `cics.screens_out`. Each entry is one screen, shown 24 by 80 with its fields, attributes and cursor position.
5. Check that `cics.terminal_waits` contains no entry with `answered: false`. Such an entry means that a task waited for a screen that the input did not supply.

You can also run the transaction from a 3270 emulator. For details, see [CICS transactions](/harwell/online-runs#3270-terminal-access).

## Step 5: Compare the results with the mainframe

Instead of comparing output by hand, state the expected results with the run. The report then carries a verdict in `oracle`.

**To compare a batch run with the mainframe**

1. Supply the mainframe's output data sets and tables as the expected end state.
2. Optionally, supply a mask for the bytes that the comparison ignores, such as the CPU and elapsed times in the job log.
3. Run the job. The report gives a verdict for each data set and table. For a data set that differs, it names the first record and byte that differ.

**To compare a transaction with the mainframe**

1. For each screen, state the map and the field values that it must show:

   ```json
   {"exact": true,
    "screens": [{"map": "CUST1A", "fields": {"MSG": "ENTER ACTION AND PRESS ENTER"}}]}
   ```

   `exact` also requires the number of maps sent to match. A field with the value `null` must be on the map, and its value is not compared.
2. Run the transaction. The report gives a verdict for each screen.

<Note>
The process exit code does not indicate whether a job succeeded. Read `status` and each step's `rc` in the report. If `fidelity.status` is `degraded`, look up each entry of `fidelity.divergences` by its `kind` in [Known limitations](/harwell/known-limits).
</Note>
